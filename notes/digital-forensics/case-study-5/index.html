02

Email Analysis & Sender Verification

To find the true routing path of a message, the email headers can be examined. Headers contain the sender and recipient addresses, Return-Path, Reply-To, Message-ID, timestamps, and authentication results. The Received fields track the IP address of every MTA the email passes through. Those fields are read from the bottom up, so the lowest entry shows the originating server. They must be interpreted carefully: they show the path, but they do not prove where the attacker was physically located.

SPF, DKIM, and DMARC are protocols used to reduce spoofing. SPF verifies authorized sender IPs, DKIM provides a cryptographic signature, and DMARC defines policy for handling failed checks. These results help show whether an email came from the domain it claimed. If a check fails, the message is more likely to be suspicious. The protocols are not always configured correctly, however, and the From address can still be spoofed because SMTP does not verify that field—the sender can enter any address. (Nelson, Phillips, & Steuart, 2019)

03

Endpoint & Network Correlation

Investigators should never click a malicious link on a live host. URLs should be examined in an isolated environment, such as a virtual machine. Investigators can also scan links with free tools to check website age, since newly registered sites are more likely to be fake.

Browser artifacts such as session cookies and cache can show that the user visited the phishing page. Browser history shows when the page was visited, and login records show where and when authentication occurred. A login from an unfamiliar location supports the conclusion that a stolen password was used. One log is not enough on its own; firewall logs and DNS requests must be correlated to reconstruct the full attack chain.

04

Incident Sequence Summary

The incident began when an email bypassed filtering via spoofing. The user was socially engineered into clicking a malicious link. The message was designed to create urgency by claiming the account would be shut off—a tactic meant to push fast action. The link redirected the user to a fake portal where credentials were entered. The attacker then used those credentials to log in from suspicious IP addresses.

Authentication logs support that the credentials were stolen and then used to access the corporate environment and view or exfiltrate sensitive data. Remediation should include changing the user’s password, blocking the malicious website, and enabling two-factor authentication so that knowing the stolen password is not enough to enter the system. The second factor can be a prompt on a known device, a verification code sent to a phone number, or a similar challenge. (HackTricks, n.d.)

05

Investigation Challenge: Attribution & Geolocation

A foreign IP associated with malicious activity does not prove the actor was physically located in that country. The traffic may have traveled through a VPN, proxy, Tor, or other masking methods. IP geolocation databases are not always accurate, and attackers can route traffic through compromised machines. (NHI Mgmt Group, 2026)

Authentication logs only prove that credentials were used from a given IP address. They do not identify the person behind the keyboard or establish the attacker’s true physical location.

06

Conclusion

The defensible conclusion is that a phishing message led to credential capture and later reuse against corporate systems, as shown by correlated email, browser, DNS, firewall, and authentication artifacts. Those logs do not establish the attacker’s physical location or personal identity.
