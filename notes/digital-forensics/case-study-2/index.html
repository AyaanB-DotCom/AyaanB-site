The Deleted Project Files

A forensic analysis of recovered Windows deletion artifacts—and the line between proving that files were deleted and proving who deleted them.

01

Executive Summary

This document presents findings concerning project files that disappeared from a shared workstation. A forensic image of the workstation was examined to determine what happened to the files and whether the available artifacts supported a conclusion that they had been stolen.

The examination recovered evidence of deletion from the Windows Recycle Bin and Master File Table. Those artifacts establish that project files were deleted and support a timeline, but the available evidence does not establish who physically performed the deletion or whether it was intentional. Security Event Logs and Registry data that could have provided corroborating context were not available in the case image.

03

Technical Analysis & Investigation Questions

Evidence of deletion
When a file is sent to the Windows Recycle Bin, Windows stores the renamed file content in a $R file and creates a paired $I metadata file containing information such as its original path, size, and deletion time. These artifacts support the conclusion that the files were deleted through the Recycle Bin. (IT-Connect, 2026)
Data persistence
Deletion does not necessarily erase file content immediately. File-system records can mark space as available for reuse while data remains recoverable until it is overwritten. Recoverability depends on the storage medium and system behavior; for example, SSD TRIM can reduce or eliminate the recovery window. (GeeksforGeeks, 2026)
Unallocated space
Unallocated space is storage that the file system considers available. Deleted content may remain there until reuse, allowing forensic tools such as Autopsy to locate or carve recoverable data. (Pen Test Partners, 2025)
Slack space
File slack is the unused portion of a file’s final allocated cluster and can retain residual data. It is distinct from MFT record slack, though both can contain useful remnants. In this case, five files were recoverable because the relevant data had not been overwritten. (TechTarget, n.d.)
Value of metadata
Metadata can contribute time values, file location, size, and allocation status, helping reconstruct the original location and timeline. Copies used in the investigation should preserve these details. (Sygnia, 2025)
Recovery versus attribution
Recovery requires locating data that remains on disk. Attribution requires additional evidence linking an action to a specific person. Here, the artifacts show which files were deleted and associate them with an account context, but they do not establish who clicked delete. (Nelson et al., 2019)
Additional artifacts
Useful corroborating sources could include Windows Event and Security Logs, Registry artifacts, browser and command history, cloud-storage audit logs, the USN Journal, LNK files, and relevant physical-access records.

04

Limitations

The absence of Security Event Logs and Registry data left gaps in determining which account session was active and what activity surrounded the deletion. The analysis therefore focused on the Recycle Bin and MFT artifacts available in a single forensic image. Activity originating from a different device or location would not be visible in that image.

The recovered files represent data that remained available; the investigation cannot measure what had already been overwritten or otherwise made unrecoverable. Most importantly, recovery verifies the prior existence and deletion of data, not the identity or intent of the person responsible. (Kent et al., 2006)

05

Investigation Challenge

If five deleted project files are recovered, can the evidence establish that the suspected employee deleted them intentionally? The answer is no. The artifacts support that deletion occurred within a particular account context, but alternative explanations remain.

Another person could have used the suspected employee’s credentials or accessed the shared workstation while that account was active. Digital evidence from the available image cannot resolve that possibility without corroboration such as physical-access records or security footage.

Malware could also have acted through the account. Evaluating that possibility would require additional workstation evidence, including relevant memory, process, persistence, and log artifacts. Establishing intent would require corroborating evidence connecting the employee’s actions to the deletion and showing circumstances consistent with a deliberate act.

06

Conclusion

The defensible conclusion is that the project files were deleted and that the recovered artifacts associate the deletion with the suspected worker’s account context. The evidence does not establish that the worker personally performed the deletion, that files were exfiltrated, or that the deletion was intentional.
