Recovering a Disabled iPod Touch 5

An authorized, data-preserving recovery that moved beneath iOS—from an A5 bootrom exploit to a temporary SSH environment and a patient offline attack against the device keybag.

Case study · Approximately 5 minutes

Target
iPod touch 5 (iPod5,1)
Platform
iOS 9.3.5, 32-bit Apple A5
Method
checkm8-a5, SSH ramdisk, offline keybag attack
Result
Passcode recovered; data preserved

Authorization

Owner permission was the starting condition.

This recovery was performed with the device owner’s explicit permission. The passcode remains redacted. Accessing a device without authorization is illegal; the work described here is a record of an authorized recovery, not permission to use these methods elsewhere.

01 / Introduction

The recovery problem

The iPod was permanently disabled after too many incorrect passcode attempts. Restoring it through iTunes would make the device usable again, but only by erasing the data that made the recovery worth attempting.

The target was an iPod touch 5, model iPod5,1, manufactured in the second half of 2015 and running iOS 9.3.5. It used a four-digit numeric passcode and an Apple A5 system-on-chip. Those details determined the entire investigation: the passcode space was finite, and the 32-bit hardware belonged to a security generation that could still be approached below the operating system.

The objective was deliberately narrow: recover access without a factory reset, preserve the owner’s data, and disclose neither the recovered passcode nor the private contents of the device. The full device profile and recovery objective are recorded in the repository’s introduction.

02 / Security boundary

Why the hardware generation mattered

Normal recovery mode begins at iBoot and is designed around signed firmware. DFU mode begins earlier, in the Boot ROM—the first immutable code executed by the chip. The public checkm8 family of vulnerabilities targets that lower layer. On an affected device, a successful exploit can change what the boot chain will accept for the current session, making it possible to start a purpose-built recovery environment without installing it permanently.

The A5 chip required an A5-specific path and precise USB behavior. A Raspberry Pi Pico running checkm8-a5, connected through a USB OTG adapter, acted as the host that delivered the exploit while the iPod was in DFU mode. A successful run left the device in “pwned DFU,” ready to accept the next stage of the recovery chain.

Architecture also defined the limit of the method. This 32-bit generation predates the Secure Enclave design introduced with the A7. On newer hardware, passcode key derivation and retry delays are enforced by a separate security processor. Here, the relevant work could still be performed on the device’s main processor once an appropriate environment was running. The repository explains both the bootrom exploit and the 32-bit versus 64-bit boundary in detail.

03 / Low-level access

Reaching pwned DFU

The first useful state had no user interface at all. The iPod entered DFU with a black screen, stopped at the Boot ROM, and waited for USB instructions. The Pico delivered the checkm8-a5 payload; the device was then transferred to the Parrot OS host for the remaining work.

  1. Enter DFUStop the boot process at the Boot ROM, below Recovery Mode and iOS.
  2. Exploit the A5Use the Pico and OTG adapter to place the device in pwned DFU for the current session.
  3. Change hostsMove the prepared device to the analysis computer without allowing a normal boot.
  4. Boot the ramdiskUse Legacy-iOS-Kit to send a patched kernel and temporary SSH-enabled environment.

This separation of roles mattered. The Pico existed to solve the A5 exploit-delivery problem; Legacy-iOS-Kit handled firmware selection, the ramdisk, and the tethered boot workflow. The hardware setup and complete exploit chain remain on GitHub for readers who need the procedural record.

04 / Temporary environment

Working around iOS without replacing it

Legacy-iOS-Kit booted an SSH ramdisk: a minimal operating environment held in memory rather than installed over the owner’s system. Through a USB tunnel, I could reach its SSH service, mount the iOS filesystem partitions, and inspect the user-data volume while the ordinary lock screen was not running.

The disabled state and the passcode were separate problems. SpringBoard preference files recorded failed attempts and enforced the visible lockout. Removing that lockout state made another eventual unlock possible, but it did not reveal the passcode or decrypt protected files. The cryptographic work still had to happen against the System Keybag.

This distinction kept the recovery honest: clearing an interface-level lockout was not treated as breaking the device’s encryption. It only prepared the device for the moment when the correct passcode was known. The repository’s technical process preserves the mount, transfer, and lockout-state steps that are intentionally omitted here.

05 / Recovery

A slow attack against the keybag

The useful breakthrough was not a shortcut around the passcode. It was the ability to test the complete four-digit space on the authorized device, using the device-bound cryptographic material that could not be moved to a faster computer.

The ARMv7 bruteforce utility from the iphone-dataprotection project read the System Keybag and tested candidates from 0000 through 9999. For each candidate, it derived a key using the passcode and the A5’s hardware-bound UID material, then checked whether the protected device key decrypted into a valid structure. A match identified the passcode without sending repeated guesses through the lock screen.

  1. 10,000 possible codes

    A four-digit decimal passcode produces a bounded search space. The attack was exhaustive rather than predictive; it did not depend on personal information or a list of likely codes. See the search-space calculation →

  2. Hardware acceleration was unavailable

    The faster IOAESAccelerator path returned e00002c1, indicating that the unpatched kernel would not grant the required privilege. Rather than introduce another kernel modification, I continued with the reliable software path at roughly six seconds per attempt.

  3. The passcode was recovered

    The correct candidate appeared after approximately 6.5 hours. It remains redacted in both publications. The owner’s data stayed intact, and the result could be used at the genuine lock screen after a tethered boot.

The complete documentation explains how the keybag test works and contrasts the software and hardware-accelerated paths.

06 / Reflections

Reliability mattered more than speed

The six-second attempt rate was difficult to accept because a faster route appeared to be close. But patching the kernel to reach the AES accelerator would have added risk and another failure surface to a data-preservation job. Once the software attack was progressing, leaving it alone was the safer engineering decision. Patience—not maximum throughput—completed the recovery.

The surrounding problems were smaller but revealing. The ramdisk exposed parts of the filesystem as read-only. Modern SSH clients rejected algorithms used by the iOS 9 server. After the lockout preferences were cleared, the device entered a recovery-mode loop and needed Legacy-iOS-Kit’s “Just Boot” path for a tethered return to the lock screen. None of these issues changed the cryptography, but each could have stopped the investigation if treated as a dead end. The technical challenges retain the errors and their resolutions.

The result also has a narrow scope. It depended on physical access, an exploitable A5 bootrom, a legacy 32-bit security architecture, and a four-digit code. It is not a general technique for modern Apple devices, where the Secure Enclave changes the trust and rate-limiting model. The repository documents those limitations alongside the project’s lessons learned.
